# macOS VM / Sandboxing Landscape for AI Agents (as of October 2026)

Research date: 2026-10-22. All "accessed" dates refer to retrieval on this date. Capabilities are marked CONFIRMED (source verified), ABSENT (searched, no evidence found), or UNKNOWN (could not determine). Context: zoo runs API-created macOS VMs on Apple Silicon via Virtualization.framework (custom supervisor zoovm) with APFS-clone base images, full-memory suspend (~25s for 8GB) / saved-state resume (~9.7s), ~69s cold clone-to-running, APFS-clone snapshots of stopped VMs, and per-clone fresh SSH host keys.

## Key Question 1: Does ANY provider offer macOS sandboxes/VMs via API for AI agents?

### Takeaway
Yes, but narrowly: the only mainstream agent-sandbox vendor shipping macOS via API is Daytona, whose macOS sandboxes are actually a third-party platform (use.computer) running on a *reserved, dedicated* Mac per account — a static allocation model, not pooled multi-tenant orchestration. Every other major agent-sandbox provider (E2B, Modal, Morph, Blaxel, Fly.io, Runloop, TensorLake, Browserbase) is Linux-only, and the Mac-in-cloud players that exist (MacStadium Orka, AWS EC2 Mac, GitLab/GitHub CI) are CI/CD-oriented with no agent API or no VM layer at all. No provider found offers API-driven macOS VMs with memory saved-state suspend/resume.

A macOS sandbox is an isolated macOS environment that runs on dedicated Apple silicon hardware. Each sandbox runs on a Mac **reserved for your account**... control the desktop through Computer Use, VNC, and SSH." — [Daytona macOS Sandboxes docs](https://www.daytona.io/docs/en/macos-sandboxes) (accessed 2026-10-22; docs footer © 2026 Daytona Platforms, Inc.)

## Key Question 2: Apple Virtualization.framework ecosystem — memory save-state / suspend-resume support

### Takeaway
Apple's framework gained VM save/restore support in the macOS 14 (Sonoma) era, but adoption is sparse and restrictive: Tart supports suspend for **macOS guests only** (Linux guests explicitly cannot suspend), Anka 3 only got ARM suspend via its GUI with CLI suspend still falling back to a full stop, and the only tool found that fully exposes *live snapshots (disk+memory) and suspend/resume for both macOS and Linux guests* is MacVisor — a brand-new (Oct 16, 2026) single-Mac desktop/CLI beta, not a cloud API. No project publishes resume-time benchmarks.

### Cited Findings
- **Apple framework capability (context):** Apple's Virtualization documentation covers starting, pausing, and resuming VMs, and the framework's save/restore API era began with macOS 14 (confirmed indirectly: Anka's early-3.x release notes state "suspending is not supported by Apple yet" before Apple added it, and later notes describe suspend becoming available with caveats). — [Apple Virtualization framework docs](https://developer.apple.com/documentation/virtualization) (accessed 2026-10-22); [Anka CLI release notes](https://docs.veertu.com/anka/anka-virtualization-cli/release-notes) (accessed 2026-10-22)
- **Tart — CONFIRMED suspend for macOS guests only; no live memory snapshots:** A Tart CLI reference lists `suspend — Suspend a VM`; a Tart issue reports Debian (Linux) suspend failing with "restoring VM state from a snapshot... failed to restore with error 'invalid argument'. unfortunately only macOS VMs can be suspendable." — [BK's Blog: Tart CLI commands](https://www.bkurtz.io/posts/tart) (as of Tart 2.28.2, mid-July 2025); [openai/tart issue #796](https://github.com/openai/tart/issues/796) (accessed 2026-10-22). Live snapshotting (memory+state while running) remains a requested feature — [openai/tart issue #147 "Live snapshotting in tart"](https://github.com/openai/tart/issues/147) (accessed 2026-10-22). **No published resume-time benchmarks found (UNKNOWN).**
- **Third-party VZ tooling historically couldn't save state at all:** A 2025 review of running Windows 11 via Virtualization.framework/Tart notes "Suspend and resume. Apple's framework refuses to save the VM" for Windows guests. — [Mustafa Akın: Running Windows 11 with Virtualization.framework](https://mustafaakin.dev/blog/windows-on-tart) (2025)
- **UTM (early 2024, VZ backend):** UTM's developers claimed firsts "no one has really done... (snapshots, suspend & resume...) with the new Apple framework yet" — indicating the state of the art in early 2024 was nascent. — [HN thread on Tart/VZ, Jan 2024](https://news.ycombinator.com/item?id=39059100). UTM's current save-state status: UNKNOWN (not re-verified).
- **MacVisor (ScaleNinja) — CONFIRMED, the only full save-state implementation found in VZ tooling:** launched in public beta October 16, 2026: "Take a disk-only snapshot, or a live one that includes memory so the VM resumes exactly where it was. Revert to any snapshot, or start a new VM from one... fork a stopped VM in a second with a linked clone that shares its disk"; "Snapshots on the Apple Virtualization stack (disk-only and live, for Linux and macOS guests), plus suspend/resume... instant linked clones on ASIF layers." Requires macOS 27 host on Apple Silicon. Caveat: "Suspended VMs and live snapshots are only meant to restore on the build that made them." — [ScaleNinja blog: MacVisor, 2026-10-16](https://scaleninja.com/blog/macvisor); [MacVisor vs Orka Desktop comparison](https://scaleninja.com/macvisor/vs/orka-desktop) (accessed 2026-10-22). **No resume-time numbers published (UNKNOWN).**
- **Anka 3 (Veertu) — CONFIRMED ARM suspend via GUI only, with hard caveats:** Release notes (Anka 3.5.0.x era): "Improvement: On ARM, you can now suspend VMs from the Anka App/UI. **Note: Suspending from the CLI/Terminal will still stop the VM** when issuing the suspend command due to an inability to move a suspended VM from one host to another (Apple limitation)." And from early Anka 3: "The `anka create` command will now produce `stopped` state VMs (suspending is not supported by Apple yet)." — [Anka CLI release notes](https://docs.veertu.com/anka/anka-virtualization-cli/release-notes) (accessed 2026-10-22)
- **Who uses saveRestoreSupport in production:** MacVisor (live snapshots + suspend/resume, Oct 2026 beta), Tart (macOS-guest suspend), Anka 3 (GUI-only suspend). No other production tooling surfaced in searches (searched 2026-10-22).

### Inferences
- The save/restore API exists but has rough edges visible in public issue trackers (Linux guests unsupported, suspended VMs non-portable across hosts, tooling version-lock on restore). zoo's ~9.7s resume and 25s/8GB serialize are consistent with what the API makes possible, but zoo's use of it in an API platform appears unique; even Tart stops short of live snapshots and Linux guest support.
- MacVisor's launch (a solo-founder CloudStack veteran) validates that "treat the Mac like a hypervisor host" is a recognized product gap — but its delivery vehicle is a local desktop/CLI app for one Mac, not a networked, multi-node, API-driven platform.

### Gaps
- Exact `saveRestoreSupport` enum values and Apple's documented guest/hardware restrictions were not pulled from the primary API page (fetch not performed); marked via secondary sources.
- No published resume-latency benchmarks exist for Tart, MacVisor, Anka, or UTM save-state (all UNKNOWN) — zoo's 9.7s figure appears to be the only public number in this category.
- VirtualBuddy and VMware Fusion (VZ-based or partially VZ-based) current save-state support not individually verified.

## Key Question 3: MacStadium Orka — snapshots/suspend-resume, API latency

### Takeaway
Orka is the most mature API-driven macOS VM orchestration platform (Kubernetes + REST since 2020), but on Apple silicon — the hardware relevant to agents — it supports **neither stop/start nor suspend/resume** (explicitly Intel-only operations "due to Apple"), and snapshots are "not its focus." No API latency figures are published.

### Cited Findings
- **CONFIRMED — Apple silicon nodes lack the full VM lifecycle:** MacStadium docs state: "The following operations are not supported on Apple silicon-based nodes: VMs: stop, start, suspend, resume (these are Intel-only operations due to Apple..." — [Orka Apple silicon support docs](https://docs.macstadium.com/orka/orka-resources/apple-silicon-based-support) (accessed 2026-10-22)
- **CONFIRMED — snapshots not a focus; ephemeral reset model:** third-party comparison table rates Orka Desktop's "Snapshots and saved state" as partial: "Ephemeral VMs reset on recycle; snapshots are not its focus" (versus MacVisor's full disk+memory snapshots, suspend/resume, linked clones). — [ScaleNinja: MacVisor vs Orka Desktop](https://scaleninja.com/macvisor/vs/orka-desktop) (accessed 2026-10-22)
- **CONFIRMED — Orka 3.x recent state:** Orka 3.5.0 (2025) added Harbor OCI registry storage for VM images and "lays the foundation for... full macOS 26 host support in Orka 3.6.0"; as of Orka 3.6, host nodes default to macOS 26.6.2; images distributed as OCI artifacts (e.g., `ghcr.io/macstadium/orka-images/golden-gate:latest` for macOS 27). — [MacStadium blog: Orka 3.5.0](https://macstadium.com/blog/orka-3-5-0); [Orka compatibility matrix](https://docs.macstadium.com/orka/orka-overview/compatibility-matrix) (accessed 2026-10-22)
- **CONFIRMED — CI/CD-centric identity:** "Orka integrates with CI tools... dynamically provisioning VMs"; positioned for Enterprise CI/CD, VDI, and AI workloads; runs on MacStadium cloud, on-prem, or on AWS EC2 Macs. — [macstadium.com/orka](https://macstadium.com/orka) (accessed 2026-10-22)
- **UNKNOWN — API latency:** no published latency figures found for Orka API operations (VM deploy time, API response time) in MacStadium docs or third-party reviews (searched 2026-10-22).

### Inferences
- Orka cannot offer zoo's core lifecycle: on Apple silicon there is no stop/suspend/resume, so no saved-state resume and (per third-party analysis) no real snapshot workflow — VMs are deploy-and-delete ephemeral. This makes Orka a CI competitor, not an agent-workspace competitor.
- Orka's OCI-image approach converges with Tart's registry model, but neither offers memory-state persistence or instant COW cloning as a productized API feature.

### Gaps
- Whether Orka 3.6+ added any Apple silicon snapshot support could not be fully ruled out from the pages retrieved, but the official Apple silicon limitations page (still live Oct 2026) says the lifecycle ops are Intel-only.
- Orka VM deploy/boot latency (clone-to-running) not found published; no apples-to-apples comparison with zoo's ~69s cold clone-to-running exists.

## Key Question 4: Anka (Veertu) — suspend/resume status and agent orientation

### Takeaway
Anka historically marketed suspend/resume as a CI fast-start feature on Intel (Hypervisor.framework era), but on Apple Silicon (Anka 3, VZ-based) suspend is GUI-only, CLI suspend silently performs a full stop due to Apple limitations on moving suspended VMs, and no resume-latency figures are published. Veertu is now pivoting messaging toward "AI coding agents" but remains CI-infrastructure (Jenkins/Buildkite/GitHub Actions runners) oriented.

### Cited Findings
- **CONFIRMED — historical Intel-era suspend/resume for fast CI startup:** Veertu's Jenkins provisioning guide ends VM prep with: "`anka stop -f` ... `anka suspend $ANKA_VM_NAME` # ... so CI can use the **super fast start-up feature** of Anka VMs," then pushes the suspended VM as the baseline registry tag. — [Veertu: On-demand macOS VMs with Jenkins and Anka Build](https://veertu.com/on-demand-macos-virtual-machines-with-jenkins-and-anka-build-for-ios-ci) (older Intel-era post, undated on page; accessed 2026-10-22)
- **CONFIRMED — Anka 3 Apple silicon suspend is GUI-only and non-portable:** "On ARM, you can now suspend VMs from the Anka App/UI. Note: Suspending from the CLI/Terminal will still stop the VM... due to an inability to move a suspended VM from one host to another (Apple limitation)." — [Anka CLI release notes](https://docs.veertu.com/anka/anka-virtualization-cli/release-notes) (accessed 2026-10-22)
- **CONFIRMED — early Anka 3 had no suspend at all:** "The `anka create` command will now produce `stopped` state VMs (suspending is not supported by Apple yet)." — [Anka CLI release notes](https://docs.veertu.com/anka/anka-virtualization-cli/release-notes) (Anka 3.0-era entry)
- **CONFIRMED — agent-adjacent pivot, CI-shaped product:** 2026 Veertu content: "AI coding agents hand commits to CI agents... On macOS and iOS, each CI agent needs a fresh VM per commit and a network boundary"; product lineup now includes "Anka MCP," "Anka Scan," and "EC2 Mac AMI Scan" alongside Anka Build/Flow; Buildkite plugin clones a template VM per job and deletes it afterward. — [Veertu: Cursor Origin, Buildkite, and Anka](https://veertu.com/cursor-origin-buildkite-anka) and [Veertu Enterprise macOS CI category](https://veertu.com/category/enterprise-macos-ci) (2026; accessed 2026-10-22)
- **CONFIRMED — density messaging:** Veertu promotes "Run concurrent Anka macOS VMs with different OS and Xcode stacks on one host: density math for vCPU and RAM." — [Veertu category page](https://veertu.com/category/enterprise-macos-ci) (2026)
- **UNKNOWN — resume latencies:** no Anka resume-time numbers found published anywhere (searched 2026-10-22).

### Inferences
- Anka's suspend/resume regression on Apple silicon (GUI-only, VMs can't move hosts while suspended, CLI = stop) reinforces that Apple's saved-state API has portability/density limitations that a platform like zoo must engineer around; nobody else is publicly claiming to have solved this at fleet scale.
- Veertu's 2026 agent framing ("network-secure disposable environments for AI coding agents") is CI-per-commit, not long-lived agent workspaces with state — a different problem than zoo's.

### Gaps

## Key Question 6: macOS security/licensing constraints for multi-tenancy — and does anyone do saved-state resume at all?

### Takeaway
Apple's macOS license constrains virtualized macOS to Apple hardware with a per-host minimum commitment (the reason AWS bills EC2 Mac hosts at a 24-hour minimum and forbids more than one instance per host), and providers handle multi-tenancy through dedicated-host / reserved-Mac allocation plus scrub-on-stop. As of October 2026, **no surveyed provider performs memory saved-state suspend/resume on macOS in any API product** — the capability exists locally (MacVisor, Tart macOS-guest suspend, Anka GUI) and on Linux clouds (Fly Machines, E2B pause), but not as a hosted macOS offering.

### Cited Findings
- **CONFIRMED — Apple SLA drives the 24-hour dedicated-host minimum:** "Billing is per second, with a **24-hour minimum allocation period** for the Dedicated Host **to comply with the Apple macOS Software License Agreement**." — [AWS EC2 Mac FAQ](https://aws.amazon.com/ec2/instance-types/mac/faqs) (accessed 2026-10-22)
- **CONFIRMED — one macOS instance per physical Mac (AWS model):** "You can run 1 EC2 Mac instance on each EC2 Mac Dedicated Host"; EC2 Mac instances are bare-metal-only. — [AWS EC2 Mac FAQ](https://aws.amazon.com/ec2/instance-types/mac/faqs); [EC2 Mac docs](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-mac-instances.html) (accessed 2026-10-22)
- **CONFIRMED — scrub-on-stop security model:** "When you stop or terminate a Mac instance, Amazon EC2 performs a scrubbing workflow on the underlying Dedicated Host to erase the internal SSD, to clear the persistent NVRAM variables, and to update to the latest device firmware. This ensures that Mac instances provide the same security and data privacy as other EC2 Nitro instances" — also preventing any saved-state/firmware-level reuse between tenants. — [AWS: Stop or terminate your EC2 Mac instance](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/mac-instance-stop.html) (accessed 2026-10-22)
- **CONFIRMED — same reserved-Mac posture at Daytona/use.computer:** "Each sandbox runs on a Mac reserved for your account" — i.e., no cross-tenant sharing of a Mac. — [Daytona macOS docs](https://www.daytona.io/docs/en/macos-sandboxes) (accessed 2026-10-22)
- **CONFIRMED — VM-per-job isolation posture in the CI world:** GitLab's macOS SaaS runners execute "each job... on a new, automatically provisioned virtual machine hosted on Apple M1 servers. The virtual machine is deleted immediately upon job completion" — [GitLab issue #342848](https://gitlab.com/gitlab-org/gitlab/-/issues/342848); Veertu: "each CI agent needs a fresh VM per commit and a network boundary" — [Veertu](https://veertu.com/cursor-origin-buildkite-anka) (2026)
- **CONFIRMED — saved-state resume exists today only outside macOS-API hosting:** Fly Machines suspend/resume (Linux) resumes "within a few hundred milliseconds" from a memory snapshot — [Fly community post](https://community.fly.io/t/new-feature-in-preview-suspend-resume-for-machines/20672); E2B "memory-preserving pause" (Linux Firecracker) — [E2B 2026 comparison](https://e2b.dev/resources/best-code-execution-sandboxes-for-ai-agents); Cua Fleet cloud explicitly "no suspend" — [Simular.ai](https://www.simular.ai/alternatives/cloud-computers-for-ai-agents). On macOS: MacVisor live snapshots/suspend-resume (local single-Mac beta) — [ScaleNinja](https://scaleninja.com/blog/macvisor); Tart suspend (macOS guests only) — [openai/tart #796](https://github.com/openai/tart/issues/796); Anka GUI-only ARM suspend — [Anka release notes](https://docs.veertu.com/anka/anka-virtualization-cli/release-notes). MacStadium Orka: suspend/resume are Intel-only operations on Apple silicon nodes — [Orka docs](https://docs.macstadium.com/orka/orka-resources/apple-silicon-based-support)
- **PARTIALLY CONFIRMED — the "2 VMs per Mac" EULA clause:** AWS's docs confirm Apple SLA constraints shape cloud architecture (24h minimum, 1 instance/host) — [AWS FAQ](https://aws.amazon.com/ec2/instance-types/mac/faqs). The exact "two additional copies or instances... within a virtual operating system environment on each Apple-branded computer" language from current macOS license agreements was not directly retrieved from an Apple primary source in this research — treat the precise clause text as unverified here (ABSENT in this research; the SLA constraint itself is well evidenced).
- **CONFIRMED — portability restriction relevant to zoo's fleet design:** Apple's framework cannot move a suspended VM from one host to another (per Veertu's release notes characterizing it as an Apple limitation) — [Anka release notes](https://docs.veertu.com/anka/anka-virtualization-cli/release-notes); MacVisor similarly warns suspended VMs only restore on the exact build that created them — [ScaleNinja](https://scaleninja.com/blog/macvisor)

### Inferences
- Industry-wide, the compliance answer to Apple licensing is *dedication, not density*: reserved Macs (Daytona/use.computer), dedicated hosts with 24h minimums (AWS), or on-prem CI fleets (Orka, Anka). zoo's APFS-clone density within the SLA's constraints is an efficiency differentiator no one else is claiming.
- The scrub-on-stop model at AWS demonstrates that incumbent clouds treat macOS state as radioactive between tenants; saved-state resume (preserving memory across sessions *for the same tenant*) is architecturally compatible with that model but nobody has productized it — zoo's ~9.7s resume of a fully warm session (guest agent intact) has no equivalent in any surveyed product.
- The fresh-SSH-host-keys-per-clone practice (re-identification) was not observed documented at any other provider; GitLab/AWS handle identity via full VM deletion or host scrubbing instead, which is far slower.

### Gaps
- Apple's current (macOS 26/27-era) macOS Software License Agreement text regarding the number of permitted VM instances per Mac could not be retrieved from apple.com in this research session.
- Whether any stealth startup offers pooled macOS VM fleets with saved-state resume could not be ruled out; nothing surfaced in searches through October 2026.
- Fly.io's original (2021–2022) macOS plans and why they never reached general availability were not re-verified from primary Fly sources; the evidence here is their absence from the current product lineup.
