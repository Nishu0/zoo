# macOS image preparation: Tart, Lume, and Zoo compatibility

Checked 2026-10-18 against official source and live GHCR registry metadata. No VM image was downloaded or booted for this research.

## Current Zoo image (local observation)

The live base's `version.json` records **macOS 27.0.1, build 26A434**. Read-only filesystem checks found an 80 GiB logical raw disk with about 28.5 GiB allocated, plus a cached Apple IPSW of 24.81 GiB. The host reports 27.0.1, but its installed build toolchain reports Swift 6.2.3 and SDK 26.2. These observations describe this machine, not published image sizes or performance guarantees. Zoo's [native bundle and install implementation](../../macos/zoovm/main.swift) is the local source of the format/version markers.

## Confirmed macOS 27 image

Cirrus publishes `ghcr.io/cirruslabs/macos-golden-gate-vanilla`. An anonymous GHCR bearer-token request followed by `/v2/cirruslabs/macos-golden-gate-vanilla/tags/list` returned **`latest` and `27.0` only**. Both manifests resolved to `sha256:b78a521145ebef24e9916c0b3999e165bb12b587d11524c5fa3ba4fe7bf79bb9`; `27.0.1` returned HTTP 404. Upload annotation: `2026-09-21T22:18:07Z`. Pin the digest rather than assuming `latest` matches Zoo's locally installed macOS 27.0.1 build 26A434. [Official package](https://github.com/cirruslabs/macos-image-templates/pkgs/container/macos-golden-gate-vanilla), [registry tags endpoint](https://ghcr.io/v2/cirruslabs/macos-golden-gate-vanilla/tags/list).

It provisions `admin` / `admin`, automatic login, and Remote Login; disables idle sleep/screensavers, screen lock, and Gatekeeper; enables Screen Sharing, passwordless sudo, and Safari automation; verifies FileVault remains off. ## Download and disk tradeoffs

The checked manifest has 69 layers totaling **30,901,319,029 bytes (~28.8 GiB)**, excluding negligible manifest/config overhead. Its uncompressed-disk annotation is **35,735,707,648 bytes (~33.3 GiB)**; neither value is the 50 GB guest-visible capacity. These are registry sizes, not measured wall-clock installation times. A prepared image avoids OS installation and Setup Assistant but requires this substantial first download plus Zoo-specific provisioning. Cache subsequent clones locally. [Pinned manifest](https://ghcr.io/v2/cirruslabs/macos-golden-gate-vanilla/manifests/sha256:b78a521145ebef24e9916c0b3999e165bb12b587d11524c5fa3ba4fe7bf79bb9).

## Compatibility with Zoo's native runner

Tart's standalone bundle contains `config.json`, `disk.img`, and `nvram.bin`. Its config embeds base64 `hardwareModel` and `ecid` representations. Zoo currently requires separate `hardware.bin`, `machine.bin`, `aux.img`, its own CPU/memory/MAC/display config, and installation/version markers. **Renaming the directory or copying only the disk is insufficient.** An importer would need validated metadata translation, NVRAM preservation, and a real Zoo boot test. This is an inference from the two implementations, not a demonstrated import. [Tart layout](https://github.com/cirruslabs/tart/blob/main/Sources/tart/VMDirectory.swift), [Tart identity encoding](https://github.com/cirruslabs/tart/blob/main/Sources/tart/Platform/Darwin.swift), local `macos/zoovm/main.swift`.

ASIF itself is supported by Tart on macOS 26+, but the checked Golden Gate creation template requires Tart 2.33+ and macOS 27 on both host and guest for automatic first-boot provisioning. Do not infer Zoo's current attachment path has been validated with ASIF. Stacked Tart images add a manifest/content-store/overlay layout and require macOS 27 plus DiskImageKit-enabled Tart; importing those is a separate problem. [Disk format support](https://github.com/cirruslabs/tart/blob/main/Sources/tart/DiskImageFormat.swift), [stacked images](https://github.com/cirruslabs/tart/blob/main/docs/quick-start.md#creating-a-stacked-disk).

## Setup and authentication boundaries

Prepared images can remove guest first-login work, but do not enroll a Zoo host or configure its authenticated guest agent. Zoo must still provision its own account/keys/agent and verify authenticated readiness; published default credentials must not become production credentials. Host enrollment and host macOS permissions remain separate. Tart also documents headless Virtualization.framework startup depending on an unlocked host login keychain. [Credentials and SSH](https://github.com/cirruslabs/tart/blob/main/docs/quick-start.md#ssh-access), [headless hosts](https://github.com/cirruslabs/tart/blob/main/docs/faq.md#headless-machines).

For Zoo's existing 27.0.1 installation path, investigate Apple's `VZMacGuestProvisioningOptions` before introducing a second VM-image format: current Tart passes those options at first boot on macOS 27 when compiled with Swift 6.4+, and its vanilla template uses them to create/login the admin account and enable SSH. This could suppress Setup Assistant while retaining Zoo's own IPSW and bundle layout; it still needs implementation and testing. [Apple API](https://developer.apple.com/documentation/virtualization/vzmacguestprovisioningoptions), [Tart start implementation](https://github.com/cirruslabs/tart/blob/main/Sources/tart/VM.swift).


## What Cua/Lume does differently

Current official Lume docs describe an offline unattended sequence: restore IPSW, boot once to materialize first-boot state, stop, patch the Data volume, boot again and verify SSH. Its built-in presets create the `lume` account, autologin and SSH without GUI clicks. **Tahoe is the explicitly verified preset**; the README records a remaining Sequoia Accessibility setup screen. These sources do not establish a verified macOS 27 unattended preset. [Official Lume README](https://github.com/trycua/cua/blob/7487f66931c696f55c392476eda2c1698376604c/libs/lume/README.md), [workflow explanation](https://cua.ai/docs/lume/concepts/how-lume-works).

The actual patcher writes the account's local-directory record/password hash, `.AppleSetupDone`, Setup Assistant preferences, SSH enablement, autologin and `kcpassword`. It specifically removes `loginwindow.AccountInfo.FirstLogins`: its comment explains that this entry can relaunch Setup Assistant even when the setup-complete marker exists. Current source hardcodes build `25F84` and product `26.5.2` for the seen-setup preferences; copying those values into Zoo's 27.0.1 guest would not be a validated fix. [Offline patcher](https://github.com/trycua/cua/blob/7487f66931c696f55c392476eda2c1698376604c/libs/lume/src/Unattended/MacOSOfflineSetupPatcher.swift), [first-boot and verification orchestration](https://github.com/trycua/cua/blob/7487f66931c696f55c392476eda2c1698376604c/libs/lume/src/Unattended/UnattendedInstaller.swift).

Lume documents `macos-tahoe-vanilla:latest` and OCI pull/push, with both legacy LZ4-chunked and newer OCI image paths. Its VM store also uses `disk.img`, `nvram.bin`, and a JSON config containing hardware and machine identifiers; it is not Zoo's bundle schema. Lumier provides a Docker-facing interface to Lume rather than a Zoo import implementation. No Lume/Lumier image was downloaded or boot-tested here. [Image commands](https://cua.ai/docs/lume/reference/cli/images), [VM layout](https://github.com/trycua/cua/blob/7487f66931c696f55c392476eda2c1698376604c/libs/lume/src/FileSystem/VMDirectory.swift), [config schema](https://github.com/trycua/cua/blob/7487f66931c696f55c392476eda2c1698376604c/libs/lume/src/FileSystem/VMConfig.swift), [Lumier README](https://github.com/trycua/cua/blob/7487f66931c696f55c392476eda2c1698376604c/libs/lumier/README.md).

## Actionable choice for Zoo

1. **Existing base repair — locally verified:** on this macOS 27.0.1 / 26A434 guest, a system `com.apple.SetupAssistant.managed` policy with `SkipSetupItems` containing `AppleID` and `iCloudStorage`, plus compatibility cloud-setup booleans, removed the remaining setup screen. The repaired base displayed Finder normally (`/tmp/zoo-base-policy-result.png`). A fresh sandbox created through Zoo's API from that template also displayed Finder (`/tmp/zoo-repaired-fresh-sandbox.png`); API command execution returned HTTP 200 / exit 0, both the command user and console user were `admin`, Finder and Dock were running, and Setup Assistant was absent. These are observed results from the local repair and fresh-clone check, not claims of coverage across every macOS release. SSH alone or a setup marker would not have established this outcome. Lume's `FirstLogins` handling remains a reference; it is not the tested fix recorded here.
2. **Fresh macOS 27 provisioning:** evaluate Apple's native first-boot API with a newer build SDK. Apple explicitly says options are evaluated only on the first boot after restore and ignored after an account has already been created, so they cannot repair the already-provisioned live base in place. [Apple API](https://developer.apple.com/documentation/virtualization/vzmacguestprovisioningoptions), [Apple's first-boot demonstration](https://developer.apple.com/videos/play/wwdc2026/224/).
3. **Prepared vanilla import:** potentially avoids restore/setup time, but requires the roughly 28.8 GiB image transfer and a validated metadata importer. It is a different macOS build, not a smaller substitute for the already cached 24.81 GiB IPSW. Preserve disk, NVRAM and machine identity as a coherent bundle; then inject Zoo identity/tools and verify a real desktop before caching it for APFS clones. No measured latency improvement or successful cross-format import is claimed.
